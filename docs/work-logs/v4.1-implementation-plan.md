**Scope**: Comprehensive v4 modernization covering all 51 feedback items + 8 learning system enhancements across 5 domain-bundled phases.

## 1. Verified Research Findings

### ✅ Confirmed Patterns (Authoritative Sources Validated)

#### 1.1 CrewAI Flows — Event-Driven Workflows

**Source**: [docs.crewai.com/en/concepts/flows](https://docs.crewai.com/en/concepts/flows)

**Verified Features**:

- `@listen` / `@start` / `@router` decorators for event-driven task coordination
- Pydantic `BaseModel` for structured state management
- `@persist` decorator with SQLite-backed ledger persistence
- `@human_feedback` for approval gates
- `or_` / `and_` conditional logic for branching
- Built-in Memory system integration
- `Flow.kickoff()` execution model

**Applicability to SOLAR-Ralph**: **HIGH**  
Event-driven decorators align perfectly with pipeline → workflow migration needs. The `@listen` pattern can replace current orchestrator tool delegation with reactive task chaining.

**Key Quote**:

> "Flows allow you to create structured, event-driven workflows... event-driven model, allowing for dynamic and responsive workflows"

---

#### 1.2 LangGraph — StateGraph with Checkpointing

**Source**: [till-freitag.com/blog/langgraph-crewai-autogen-compared](https://till-freitag.com/blog/langgraph-crewai-autogen-compared)

**Verified Features**:

- StateGraph with thread-level checkpointing and time-travel debugging
- Deterministic state transitions (vs. CrewAI role-based delegation)
- Production readiness: ⭐⭐⭐⭐⭐ (LangGraph), ⭐⭐⭐⭐ (CrewAI), ⭐⭐⭐ (AutoGen)
- GitHub stars: LangGraph 8k+, CrewAI 25k+, AutoGen 38k+
- Learning curve: LangGraph steep, CrewAI low, AutoGen medium

**Applicability to SOLAR-Ralph**: **HIGH**  
StateGraph checkpointing solves current lack of crash recovery. Thread-level state persistence enables resumable pipelines after failures.

**Key Quote**:

> "LangGraph for control freaks, CrewAI for fast shippers, AutoGen for research pipelines"

**Decision**: Use LangGraph for inner pipeline state, CrewAI for inter-agent coordination.

#### 1.3 GSD 2 — Autonomous Execution Framework

**Source**: [explainx.ai/skills/aradotso/trending-skills/gsd-2-agent-framework](https://explainx.ai/skills/aradotso/trending-skills/gsd-2-agent-framework)

**Verified Features**:

- **Milestone/Slice/Task Hierarchy**:
  - Milestone: 4-10 slices
  - Slice: 1-7 tasks
  - Task: single context window (IRON RULE)
- **STATE.md Ledger**: Auto-mode position tracking, mechanically verifiable must-haves
- **Git Worktree Strategy**: Structured commit messages, isolated branches per slice
- **Crash Recovery**: LOCK file with recovery briefing synthesis
- **Cost Ledger**: `ledger.json` with budget ceiling enforcement
- **Stuck Detection**: 2-attempt diagnostic prompts before hard-stop
- **DECISIONS.md Register**: Auto-injected into task dispatches

**Applicability to SOLAR-Ralph**: **EXTREME**  
This is the closest existing pattern to SOLAR-Ralph's intended pipeline → autonomous execution model. STATE.md ledger maps directly to current ledger structure. Stuck detection addresses current infinite loop risks.

**Key Quote**:

> "Iron rule: A task must fit in one context window. If it can't, split it into two tasks."

**Implementation Priority**: P0 — Adopt stuck detection + STATE.md ledger immediately.

#### 1.4 Castari Proxy — Model Inheritance via SDK Interception

**Source**: [github.com/castari/castari-proxy](https://github.com/castari/castari-proxy)

**Verified Features**:

- `queryCastari()` drop-in replacement for Claude Agent SDK `query()`
- **Global fetch hook interception** to inject routing headers
- `CASTARI_SUBAGENT_MODEL=inherit` for dynamic model inheritance
- Cloudflare Worker as stateless proxy (Anthropic ↔ OpenRouter translation)

**Applicability to SOLAR-Ralph**: **MODERATE**  
Not directly applicable (we don't have multi-provider needs), but the pattern of SDK-level interception validates the approach of hooking into agent execution flow before tool calls.

**Relevance**: Validates PreToolUse hook pattern for governor orchestration delegation.

#### 1.5 Context Compaction Workarounds

**Source**: [github.com/anthropics/claude-code/issues/7530](https://github.com/anthropics/claude-code/issues/7530)

**Verified Workarounds**:

- `/exit` → `/resume` → `/compact` sequence (clears compaction bugs)
- **PreCompact hook** for state handoff before compaction
- **65% threshold** for proactive session rotation (avoids hitting 80% auto-compact)

**Applicability to SOLAR-Ralph**: **MODERATE**  
Context rotation at 65% threshold aligns with research recommendation. PreCompact hook pattern can be adapted to PrePipelineTransition for ledger-based handoff.

## 5. Risk Mitigation

### v4.1: Foundation & Trust — LOW RISK

**Risks**:

- Hook debugging reveals deeper architectural issues
- File write permissions block ledger updates
- Integration testing uncovers new regressions
- Terminal cleanup fails on Windows vs Linux

**Mitigation**:

- ✅ Create backup of current v4 branch before fixes
- ✅ Test hooks in isolation (unit tests for each hook)
- ✅ Manual verification after each fix (don't batch changes)
- ✅ Cross-platform testing (Windows + Linux terminal commands)

**Rollback Plan**: Revert to v4 branch if >2 critical regressions

---

### v4.2: Architecture & State — HIGH RISK (Workflow Migration)

**Risks**:

- Workflow migration breaks existing pipelines
- Orchestrator tool restrictions too aggressive (blocks valid workflows)
- Loop invocation creates infinite loops despite safeguards
- STATE.md ledger corruption (race conditions)
- Memory consolidation breaks existing learnings
- Context compaction workaround unreliable (no pre-compact hook)

**Mitigation**:

- ✅ **Feature flag system**: `workflow_mode: pipeline | workflow` toggle in `solar.config.json`
- ✅ **Parallel architecture**: Keep pipeline files for 1 month post-migration
- ✅ **3-file exception**: Allow orchestrator classification reads (balance restriction vs effectiveness)
- ✅ **Hard iteration cap**: Max 10 iterations globally (not per task), 2-hour timeout
- ✅ **Ledger transactions**: Atomic read-write for STATE.md updates
- ✅ **Memory migration guide**: Document `/memories/repo/` → `learnings/` migration
- ✅ **Compaction testing**: Manual compaction triggers before production use

**Rollback Plan**:

- Workflow mode toggle → revert to pipeline architecture
- Ledger backup before STATE.md introduction
- Memory rollback: Restore `/memories/repo/` write access if `learnings/` fails

---

### v4.3: Agent Specialization — MODERATE RISK

**Risks**:

- Tier boundaries too restrictive (blocks valid workflows)
- Delegation chain deadlocks (circular dependencies)
- Context loss during agent handoffs
- Collector agent bottleneck (all tasks require collection phase)
- Work breakdown agent over-decomposes (100+ tasks from simple epic)

**Mitigation**:

- ✅ **Phased rollout**: Collector only → +Planner → +Implementor → +Reviewer
- ✅ **Fallback mode**: `tier_enforcement: false` config to disable restrictions
- ✅ **Handoff validation**: Schema validation for handoff templates
- ✅ **Collector bypass**: Allow orchestrator to skip collector for simple fixes (<3 files known)
- ✅ **Decomposition limits**: Max 10 slices/milestone, max 7 tasks/slice (GSD 2 pattern)
- ✅ **Parallel testing**: Run Epic 16 with/without tiers, compare results

**Rollback Plan**:

- Disable tier enforcement via config flag
- Revert to direct orchestrator → implementor delegation

---

### v4.4: Documentation Quality — LOW RISK

**Risks**:

- Docs reviewer too strict (blocks valid docs)
- Template enforcement breaks existing workflows
- Split instructions cause import errors
- Tech stack verification false positives

**Mitigation**:

- ✅ **Graduated enforcement**: Start with warnings only, add blocking after 1 week soak
- ✅ **Template validation**: Schema tests before deployment
- ✅ **Import testing**: Verify all `.instructions.md` files load correctly
- ✅ **Tech stack whitelist**: Allow multiple valid stacks per domain (e.g., Vite + Webpack for frontend)

**Rollback Plan**:

- Disable docs reviewer via agent removal
- Merge split instructions back to monolithic file

## 9. Open Questions & Design Decisions

### Architecture Questions

**Q1: STATE.md Schema Format**

- **Options**: YAML (structured parsing) vs Markdown (human-readable) vs Hybrid (YAML frontmatter + markdown body)
- **GSD 2 Recommendation**: Markdown for readability
- **Trade-off**: YAML more robust for programmatic parsing, Markdown easier for agent reading
- **Proposed Decision**: Hybrid approach (YAML frontmatter for structured fields, markdown body for prose)
- **Validation Method**: Parser test with both formats, measure agent interpretation accuracy

**Q2: Stuck Detection Threshold**

- **Options**: 2 attempts (GSD 2 pattern) vs 3 attempts (safer) vs Configurable per workflow
- **GSD 2 Recommendation**: 2 attempts with diagnostic prompt
- **Trade-off**: 2 attempts faster failure detection but higher false positive risk; 3 attempts safer but slower feedback
- **Proposed Decision**: 2 attempts with diagnostic by default, configurable via workflow metadata (`max_retry: 2`)
- **Validation Method**: Intentional stuck scenario test, measure false positive rate

**Q3: Ledger Storage Location**

- **Options**: Keep `.github/solar-system/ledgers/` vs Migrate to custom `.gsd/` folder
- **GSD 2 Recommendation**: Custom `.gsd/` folder for portability
- **Trade-off**: `.gsd/` cleaner namespace but requires migration; `solar-system/` existing structure no migration
- **Proposed Decision**: Keep `.github/solar-system/` for v4.x (avoid breaking changes), evaluate `.gsd/` for v5.0
- **Validation Method**: No action needed for v4.x (defer decision)

**Q4: Workflow Metadata Storage**

- **Options**: YAML files in `.github/workflows/` folder vs JSON in `solar.config.json` vs Hybrid (YAML per workflow + JSON global config)
- **CrewAI Pattern**: Pydantic BaseModel (structured classes)
- **Trade-off**: YAML files easier to version/diff, JSON faster to parse
- **Proposed Decision**: Hybrid approach (YAML per workflow in `.github/workflows/`, JSON global defaults in `solar.config.json`)
- **Validation Method**: Workflow load test, measure parsing time vs file size

---

### Implementation Questions

**Q5: Agent Model Inheritance**

- **Question**: Do subagents inherit invoker's model (Sonnet/Opus) or use own frontmatter model?
- **Investigation Required**: Test high-reasoning task invoked by low-tier agent
- **Potential Workaround**: Orchestrator invokes high-tier agents directly for complex tasks (bypass low-tier intermediaries)
- **Validation Method**: Create test scenario (Haiku orchestrator → Sonnet implementor), verify model used
- **Priority**: HIGH (affects v4.5 model selection strategy)

**Q6: PreCompact Hook Alternative**

- **Question**: Since `pre-compact` hook blocked by VS Code platform, what's the best polling-based alternative?
- **Options**:
  - 30-second background poll checking context% via session status API
  - Hook into every tool call, check context after each use
  - User-triggered compaction only (manual `/compact` command)
- **GSD 2 Pattern**: 65% threshold for proactive rotation
- **Proposed Decision**: Tool call hook approach (check context% after every tool use, trigger handover at 65%)
- **Validation Method**: Epic 16 with monitoring, measure compaction triggers vs false positives

**Q7: Collector Agent Bypass Logic**

- **Question**: When can orchestrator skip collector and go directly to implementor?
- **Options**:
  - Never (always collector-first for consistency)
  - Simple fixes only (<3 files explicitly listed in user request)
  - Configurable per workflow (workflow metadata: `require_collector: true/false`)
- **Trade-off**: Always collector = overhead for simple tasks; Bypass = risk of insufficient context
- **Proposed Decision**: Allow bypass for simple fixes (<3 files known), require collector for all other workflows
- **Validation Method**: Simple fix test (1-file change), verify direct orchestrator → implementor works

**Q8: Work Breakdown Decomposition Limits**

- **Question**: What are the hard limits for Milestone/Slice/Task decomposition?
- **GSD 2 Pattern**: 4-10 slices/milestone, 1-7 tasks/slice, single-window tasks
- **Question**: Should these be hard limits (block decomposition) or soft limits (warning only)?
- **Proposed Decision**: Hard limits with warning (block if exceeded, suggest re-scoping)
- **Validation Method**: Epic with 15 slices intentionally created, verify Work Breakdown agent rejects

### User Experience Questions

**Q9: askQuestion Frequency Threshold**

- **Question**: How many askQuestion calls are acceptable per workflow before causing user fatigue?
- **Options**: Max 1/workflow, Max 3/workflow, Unlimited (trust agent judgment)
- **Trade-off**: Too few = agents guess, Too many = user fatigue
- **Proposed Decision**: Max 3/workflow, batch remaining questions into single multi-question call
- **Validation Method**: User feedback survey after v4.5, measure satisfaction vs question count

**Q10: Approval Workflow Timeout**

- **Question**: How long to wait for user approval before auto-approving or halting?
- **Options**:
  - 1 hour (fast feedback),
  - 24 hours (reasonable availability),
  - No timeout (wait indefinitely)
- **Trade-off**: Short timeout = risk of auto-approving wrong design; Long timeout = delayed execution
- **Proposed Decision**: 24-hour auto-approve with notification (email/Slack if available)
- **Validation Method**: Approval workflow test with 25-hour delay, verify auto-approve triggers

**Q11: Output Verbosity Default**

- **Question**: What should be the default verbosity level for agent output?
- **Options**: `concise` (minimal text), `normal` (balanced), `verbose` (full explanations)
- **Trade-off**: Concise = faster reading but may miss context; Verbose = complete info but slower
- **Proposed Decision**: `concise` by default, user-configurable via `solar.config.json` (`output_verbosity: concise`)
- **Validation Method**: User feedback after v4.5, measure preference distribution

### Performance Questions

**Q12: Context Usage Threshold for Rotation**

- **Question**: At what % threshold should proactive session rotation trigger?
- **Claude Code Pattern**: 65% threshold to avoid hitting 80% auto-compact
- **Question**: Is 65% optimal or should it be higher/lower based on workflow type?
- **Proposed Decision**: 65% global default, allow workflow-specific override (`rotation_threshold: 70` for simple workflows)
- **Validation Method**: Monitor compaction failures at different thresholds, optimize based on success rate

**Q13: Feature Flag Rollout Strategy**

- **Question**: Should feature flags be enabled per phase or per feature?
- **Options**:
  - Per phase (all v4.2 features enabled together)

- **Trade-off**: Per phase = simpler management; Per feature = safer rollback
- **Proposed Decision**: Per feature flags with phase presets (`solar.config.json` presets: `v4.1`, `v4.2`, `v4.3`, etc.)
- **Validation Method**: Test rollback scenario (v4.3 → v4.2), verify feature flags revert correctly
