SOLAR-Ralph · v5.3 · governor-as-graph

The Agentic Harness
that makes agents finish.

“Agentic AI should finish tasks autonomously. Most of the time, it doesn’t.”

SOLAR-Ralph is an installable harness you drop into a code repository. It wraps your coding agents with deterministic control — the right specialist, the right gates, restart-safe state, auditable runs — so multi-step AI work actually completes correctly instead of declaring success early, misunderstanding the task, or losing everything when a session ends.

01What it is

SOLAR-Ralph is a five-layer protocol (the acronym) plus, in v5, a real governor-as-graph runtime. Same pillars as v4 — specialists, orchestrator, ledger, adversarial checks, recursion — but the control flow is now code (LangGraph), not a prompt-instructed state machine. One engine, and VS Code becomes just one client of many.

S
Specialist
Isolated domain agents; one failure doesn’t block the rest.
O
Orchestrator
v4: the governor agent. v5: the graph itself owns routing + gates.
L
Ledger
Restart-safe state anchor — Objective / Work Queue / Decisions Log.

Adversarial
A non-author verifies before work is trusted or written.
R
Recursive
Bounded rework loop with a declared exit condition.
The three layers (v5)

Think of it as a control system around your agents: surface (where you talk to it), control (the graph that decides), tools (repo-scoped actions), and repo truth (durable state). The guardrail: MCP = tool protocol · LangGraph = control flow · repo = durable truth. Never rebuild the vector DB or MCP runtime inside the graph.

SURFACE

Any client

VS Code Copilot agents (@Governor v5) · CLI solar-governor · HTTP/SSE later · CI. IDE-agnostic.

CONTROL

Governor graph (LangGraph, own process)

Material gate → Hermes intake → dispatch → specialist → review → complete. Interrupts for approval, SQLite checkpoint, compactor, light/full profiles.

TOOLS

MCP servers (local, repo-scoped)

Workspace (read/edit + write-guard) · exec · repo-index · optional hub uplink (owned repos only).

TRUTH

Repo-local data/context

.solar/state (checkpoint) · ledger (human view) · registry (roles/chains/playbooks) · run-cards · handoffs.

02When to use it

Reach for the harness when the work is more than a single quick edit — when you’d otherwise trust one agent to reason, act, and self-certify across many steps.

Use it when…
  • Multi-role work — an epic or story spanning design, frontend, backend, docs, review.
  • Tasks that must survive restarts — long jobs where losing state mid-way is expensive.
  • You need gates & approvals — plan approval, design preview, adversarial review before “done”.
  • Agents keep getting it wrong — early “done”, missing context, hours in the wrong direction.
  • Deterministic routing matters — the same request should route the same way, reproducibly.
  • Vendor/IDE independence — one engine, many fronts (Copilot today, anything later).
Skip it when…
  • A single, tiny change — one file, no gates needed; just ask the matching specialist directly.
  • Pure Q&A / chat — “explain this”, “what does this do” — no execution flow to govern.
  • You want zero ceremony — the harness adds gates + telemetry; sometimes that’s overhead you don’t need.
Rule of thumb: if you’d be annoyed that an agent “finished” without really finishing — that’s the pain SOLAR exists to remove. If you don’t care, you don’t need it yet.

03Why use it

Each failure mode of naive agentic coding has a named SOLAR countermeasure — and in v5 that countermeasure is enforced by graph edges and state, not by hoping a prompt holds.

The pain (agent fails by…) The SOLAR answer
Declaring the task done before it actually is Ralph Loop — bounded rework ≤ 3 + explicit exit; TASK_COMPLETE only after the gate passes.
Starting with missing context, failing mid-way Material Gate — MATERIAL_INSUFFICIENT stops the run before any specialist is dispatched.
Hours of code before you notice it misunderstood Design / intake gates — Hermes decodes intent; plans are confirmed before implementation agents run.
Self-certifying its own output Adversarial review — a non-author (Code Reviewer) verifies; read-only, catches what the author missed.
Losing all progress when the session ends Ledger + SQLite checkpoint — resume by thread id; the ledger is a render of durable state.
Changing one agent breaking the whole team Registry-as-data — roles, chains, playbooks are entries you edit; swap without rewiring.

Auditable

Every run writes a run-card (thread, role, chain, tokens, verdict) + decisions log. You can say what happened, not guess.

Deterministic

Routing is registry + graph, not vibes. Same request → same flow → replayable runs.

Cost-bounded

Compactor digests between specialists (~≤40% of raw). Profiles trade depth for tokens when you want speed.

04Where to use it

One engine, four install fronts — the same .solar runtime and registry drop into a repo, then you drive it from whatever surface fits.

IDE / Copilot

Custom agents (@Governor v5, Hermes, specialists) run the graph via the CLI. DeepSeek-through-extension, agent-dispatch runner.

CLI

solar-governor run headless. Init, doctor, run, resume — scriptable, testable.

Container

Headless cloud runs; state → volume / object store. No IDE required.

CI action

Install + run in CI, zero local setup, profile: knob. Non-interactive.

Who is it for: solo engineers & small teams who ship multi-step features with AI and want it trustworthy; repos that are AI-active (mandarin, the resume hub, any codebase you let agents edit). Not a replacement for your agent — it’s the harness around it.

05How to use it

One request, one thread, a narrated flow. Here is the whole journey at concept level.

LangGraph nodes + edges: material gate → dispatch → specialist → review → complete. SQLite checkpoint, compactor, profiles.

Deterministic. Vendor-agnostic. Headless-runnable.

Specialists

Registry roles (investigator, architect, uiux, engineers, docs, reviewer) that do the real work — chained by the governor driver, one link at a time, never spawning each other.

Hermes is confident → governor runs. Not confident → one clearance bounce (you pick) → run. Chains run under the governor driver: each link is dispatched in order and its run-card checked before the next — agents never chain to each other (pilot-falsified). Human-owned gates (e.g. UIUX design preview) pause the chain for approval.

Two run modes
Mode Meaning
Role-pinned
--role 		Hermes says “this is a backend fix” → run exactly that specialist. Deterministic, no keyword guessing.
Named chain
--chain epic 		Registry chain. In the IDE the governor driver runs each link in order — per-link dispatch, run-card checked before the next. The chain entry does not run the rest itself. investigator → architect → uiux → fe+be → docs → reviewer
Auto headless
--chain epic --auto 		Same link-by-link loop with no IDE: the driver executes every link headless (http / stub), one run-card per link, persisted under .solar/chains/.

Runners decide how a specialist executes: agent-dispatch run the repo’s IDE agent (DeepSeek via extension) http OpenAI-compatible API stub offline/deterministic tests.

Profiles
Profile Best for Gates Compactor
Light Fast-moving repos few / none off
Full Spec-driven work design + adversarial + approval mandatory

Deep trade: light sacrifices verification + gates for speed and low tokens; full keeps the judgement gates. What always survives is the parts that encode judgement.

Commands you’ll actually type

solar-governor init --repo <path> --runner agent-dispatch # install: writes .solar/ config + registry
solar-governor doctor --repo <path> --json # self-check: config · checkpoint · graph · registry · runner
solar-governor run "epic 25 …" --repo <path> --chain epic --json # run a named chain (one step, exit 10/11/0/2)
solar-governor run "fix the review endpoint" --repo <path> --role backend-engineer --result result.md # pinned specialist + resume
solar-governor serve --repo <path> # headless HTTP API: POST /run (one step) · POST /chain (auto)
solar-governor bench "verify guest gating" --repo <path> --n 5 --chain verify # N-run aggregate: tokens · duration · verdict
solar-governor eval --repo <path> --n 3 # known-answer battery → pass rate (quality signal)

In the IDE you usually don’t type these — you pick @Governor v5 and talk. Hermes + Governor translate.

Measured (mandarin pilot · 2026-09-05): eval battery holds 18/18 (100%) across tuning settings · tool-output truncation (SOLAR_TOOL_OUTPUT_CHARS=8000) is a pure win (~34% fewer prompt tokens, ~22% faster) and is the new default · an entire pilot day ran for ≈ $0.11 (input ~77% cache-hit). Cost is not the constraint — quality and wall-clock are; on heavy verifies the objective (“stop once verified”) beats any round cap.
Start small: init on a branch → doctor → run one quick --role task → then the --chain epic pilot. Every step lands a run-card you can read, so adoption is a series of reviewable runs, not a leap of faith.
